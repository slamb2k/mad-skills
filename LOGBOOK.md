- [ ] /logbook roadmap, one file per entry: replace the single LOGBOOK.md with a directory of one-entry files (the shape Claude Code's own auto-memory dir uses). Two problems collapse at once. (a) Merge conflicts: a single committed ledger written on feature branches is a conflict magnet the moment two branches are in flight — one-file-per-entry makes concurrent capture structurally conflict-free, which is the precondition for the ledger ever being safe in a multi-contributor repo. (b) The size cap and its eviction machinery exist only to keep one file readable; a directory has no such pressure, so LOGBOOK-ARCHIVE.md, relocation, victim-selection ordering, and the whole preview/breach-prompt flow can be deleted rather than maintained. Keep a generated LOGBOOK.md as a read-only index if a single-file view is still wanted. — /ship real-talk #47 ledger-timing discussion (2026-08-01)
- [ ] /logbook roadmap, post-merge queue: give session-guard a local staging area (e.g. .mad/pending-followups.json, gitignored) that logbook-capture writes to when no commit is available to carry the entry, and that /ship Stage 1b flushes into the next branch automatically. Would close the last hole left by moving capture to Stage 1b — follow-ups that only exist because of a CI failure or merge surprise still land after the merge, and today the only options are a dirty default branch or a docs-only PR. A queue keeps the default branch clean without weakening survives-/clear (the file is on disk, just uncommitted). — /ship real-talk #47 ledger-timing discussion (2026-08-01)
